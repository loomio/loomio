# Loomio 3.4.0

This is another important refactor for the system - it paves the way for mobile
notifications, "1 email per day" batched notifications, and per-group summary
emails.

- **New:** Separate topic timeline items from notification processing
- **New:** Record each in-app, email, and chatbot delivery for its recipient and channel

From a developer point of view, this release is a continuation of the
refactoring work started in 3.1.0 (poll comments).

Regular readers of release notes (hello!) may remember that in 3.1.0 we
introduced the `Topic` model - which was given all the logic about what a
thread is in Loomio - so that you could have comments on a poll or a discussion.
So now a `Discussion` record has about as much logic as a `Comment`, and it's
effectively just a comment, with a title, that anyone can edit, and it's the
first item in the thread.

Now we're introducing the `TopicItem` model. The `Event` model was carrying
responsibility for positioning items in a thread, as well as notifying people
about stuff as it happened. Now those are separate: `TopicItem` and
`Notification`.

The rest of these release notes were written by Codex. Its concise explanation
might make more sense after reading what I just wrote:

Loomio 3.4.0 separates topic timeline items from notifications and introduces a
durable delivery record for each notification recipient and channel. This is a
breaking database and API change with an irreversible migration.

## Notification delivery

A notification represents one logical occurrence. Each in-app, email, or
chatbot delivery is stored separately with its recipient, status, availability,
attempt history, and provider state. In-app read state belongs to the
recipient's delivery.

Explicit audiences, including mentions, replies, invitations, and recipients
selected by a coordinator, are recorded when the notification is created.
Broader audiences (groups, subgroups, voters, nonvoters, and others) are
resolved by background workers. Email and chatbot jobs normally start as soon
as their delivery rows are created and make up to five delivery attempts.

## Topic items

Discussion and poll timeline activity is now stored in `topic_items`. Topic
items always belong to a topic and retain their sequence, ancestry, pinned
state, actor, and underlying discussion, comment, poll, stance, or outcome.
Notification processing no longer depends on using the same record as both a
timeline item and a delivery operation.

The migration removes legacy operational events that were not publishable on a
topic. If one of those events was the parent of a surviving timeline item,
Loomio reconstructs that topic's ancestry, sequence metadata, positions, child
counts, and reader ranges before validating the new parent/topic database
constraint.

See [PR #12768](https://github.com/loomio/loomio/pull/12768) for the complete
notification-delivery and topic-item change.

## Integration compatibility

The B2 API supports integrations acting as a Loomio user. This release changes
one B2 response that integration owners should review. The route
`GET /api/b2/threads/:id/items` and its `items` response root are unchanged,
but each item is now serialized as a topic item:

- `eventable_type` and `eventable_id` become `itemable_type` and
  `itemable_id`.
- Nested parents use `parent_topic_items` instead of `parent_events`.
- Timeline items no longer include `custom_fields` or `recipient_message`.

Other B2 routes are unchanged. The B3 API, which supports server-based
integrations, has no route, controller, or response changes in this release.

V1 API changes are internal to the Loomio client and are not included in this
integration compatibility summary.

## Export and database compatibility

Consumers of group JSON exports or the Loomio database schema must be updated
with the application:

- Group JSON exports contain `topic_items` instead of `events`, and include
  `notification_deliveries` alongside logical `notifications`.
- The Rails `Event` model and `events` table are replaced by `TopicItem` and
  `topic_items`.

## Upgrade

For most instances, make and verify a current database backup, set
`LOOMIO_CONTAINER_TAG=3.4` in `.env`, then run:

```sh
./update.sh
```

No separate backfill command is required. Loomio remains unavailable while the
migration consolidates notification history, audits the result, and performs
the final schema cutover.

During `db:migrate`, Loomio:

1. prepares the notification and delivery tables if they do not exist;
2. consolidates legacy per-user notification receipts in resumable batches;
3. performs a complete low-ID repair and consistency audit;
4. replaces the legacy notifications table only after the audit reports no
   blocked, missing, or extra notification and delivery identities; and
5. replaces legacy events with validated topic items.

Allow a maintenance window based on the size of the `notifications` and
`events` tables. In a production-sized rehearsal, the initial consolidation
processed about 675,000 legacy notification receipts per minute. The mandatory
full audit took about three minutes, with final schema and topic-item work
adding further time. Throughput depends on the database hardware and data
shape.

Consolidation batches commit independently. If the upgrade stops before the
final table replacement, rerun `./update.sh`; the migration resumes from its
stored cursor. Do not manually delete the preparation tables or alter the
cursor.

## Optional online warm-up

Instances that must meet an uptime guarantee can first install
[Loomio 3.3.999](2026-08-27_v3.3.999.md) and run its notification consolidation
while Loomio remains available. The 3.4.0 update then processes only later
receipts before running the mandatory full audit and cutover.

After the warm-up finishes, make and verify a fresh database backup, set
`LOOMIO_CONTAINER_TAG=3.4`, and run `./update.sh` normally. Do not run the
3.3.999 consolidation command after starting the 3.4.0 update.

## Rollback

The notification and topic-item cutover is intentionally irreversible. After
the migration succeeds, Loomio 3.3 cannot use the 3.4 database schema, and a
Rails migration rollback cannot reconstruct duplicate legacy notification
receipts or the removed operational events.

To return to Loomio 3.3, restore the database backup made immediately before
the upgrade and deploy the matching 3.3 application version. Do not deploy a
3.3 container against a database that has completed the 3.4 migration.
