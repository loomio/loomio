# Git and pull-request instructions

## Git commits and attribution

- Do not run `git commit` unless the user explicitly asks for a specific commit.
- Permission to commit once does not grant permission to commit again later without asking.
- If the user asks you to commit and then asks you to do more work, you need explicit instruction to commit again before making another commit.
- Write concise commit messages that explain what changed and why it was necessary. Use one or two sentences for each distinct fix; issue IDs are optional context and must not replace the explanation.
- When fixing multiple issues, make small, specific commits rather than combining unrelated fixes. Keep each commit independently coherent and include its relevant tests.
- Do not self-reference or market the agent in branch names, commit messages, PR titles, PR descriptions, or any other project-facing metadata. Avoid agent/tool names, prefixes, or attribution such as `codex/`, `claude/`, `copilot/`, `generated by`, or similar.

## Pull requests

- Include a `Performance impact` section in pull-requests that have significant potential for changing performance. Explain the effects that matter to a web application: database query count and cost, request and background-job latency, response and realtime payload size, server memory, and browser requests, processing, and rendering. State when there is no meaningful impact.
- Describe both ordinary use and the worst case, including how cost scales with page size, conversation depth, or other relevant inputs and whether it is bounded. Use measurements when practical; distinguish measured results from estimates and identify what was not measured. Do not describe batched queries as a constant overhead when the number of batches grows with the input.
