# Permission-test audit review

This review accompanies the mutation audit because Loomio's agent instructions require direct security review and focused regressions for permissions, authentication, sessions and voting. Application code, schema and policy definitions remain fixed during the test comparisons. The measurement and behavioral-review ledgers describe the scope completed so far; this document does not certify every access path as secure.

The existing access-control fixture matrix remains the common source for members, topic guests, unrelated groups, non-guest readers, revoked access, inactive accounts and conflicting preferences. The former-member guest fixture represents a new guest invitation after membership revocation. It does not imply that revoking membership preserves guest access. New permission examples use the named group and direct topics and retain distinctions between group coordination, topic coordination and instance administration.

The `admin` fixture is both a group coordinator and an instance administrator. Suspension tests therefore promote an ordinary named member when they need to prove that group coordination alone does not bypass suspension. The separate `server_admin` fixture tests an instance administrator with no group relationship. Raw ability predicates and authenticated request checks remain separate boundaries: an inactive account can still have an active coordinator membership in the database, while authentication rejects its requests.

New regressions cover ownership of identities, bookmarks, tasks, membership records and account preferences; visibility delegated through polls and topics; denied comment deletion; coordinator-only webhook destinations; attachment deletion after suspension or discard; membership invitation state and self-promotion; and session-backed channel access. The stance delegation tests concern identified polls. Permission to read a stance does not establish that its reason or choices may be serialized while results are hidden; the existing query, serializer, timeline, realtime, notification, mail, search and export contexts remain necessary.

Direct secret-group page requests now deny signed-out visitors, topic guests, revoked access, outsiders and unrelated instance administrators through both handles and keys. Reader-list tests distinguish ordinary guests, who see their own email, from topic coordinators, who can see other readers’ addresses, on both group and direct topics.

Topic invitation checks now target `Topic`, matching `UserInviter` and `UserQuery`. Three discussion-based denial assertions previously passed because `Discussion` has no `add_guests` rule. The corrected cases and new named role checks distinguish group membership from direct-topic guest membership, group coordination from topic coordination, and verified group-member discovery from direct-topic discovery. Suspended and discarded groups must also deny stance invitation redemption/resending and redaction/restoration, each tested from an initially permitted state.

Group invitation tests separately exercise signed-out and signed-in bearer access to a secret group's metadata. A group token must match the requested group; a membership token must identify a pending, unrevoked invitation in that group. Neither token alone grants private-content access or subscription permission. The named parent/subgroup roles distinguish private group content from publicly visible metadata and inherited parent-member access. Move destinations distinguish verified group coordinators, members with permission to start discussions, topic-only coordinators and outsiders; unverified members and coordinators are denied. Existing follow, membership-list and topic-move controller/service cases are included in the group-rule matrix. The legacy `Group#add_guests` rule remains recorded separately from the actual topic invitation workflow.

Member name changes now distinguish verified nameless accounts from unverified named accounts, while an ordinary group coordinator cannot rename a verified named peer or an outsider. Membership-list tests require coordinator-only peer email visibility and suppress peer weight/email fields, including the nested user payload, for ordinary members. Pending SSO identities must remain unlinked and leave the signed-in account profile unchanged even when login profile synchronization is enabled.

SAML tests now require Loomio's callback/logout URLs, issuer, NameID format, SHA256 algorithms and signed-assertion setting passed to the provider library, plus explicit opt-in for identity-provider-initiated login. They stub the provider validity verdict and therefore do not establish end-to-end XML signature verification. Passkey failure checks require the generic rejection response and unchanged sign counter/last-used state before session creation. Existing CSRF, challenge replay, recent-authentication and credential-ownership tests remain necessary.

Browser consent for mobile authentication now requires an authenticated browser session before approving a pending request. Requests expire at the exact deadline, are consumed on expiry or successful approval, and cannot produce another authorization code on replay. Invalid clients, callbacks and malformed proof parameters are rejected before authentication; duplicate checks cover every security parameter. Approval and denial responses retain the original state and omit the opposite result key. The consent response requires `no-store`; it passes independently of the separately reproduced bootstrap header defect. These controller cases do not replace the authentication service's PKCE, authorization-code redemption, token rotation/reuse and device/session-revocation tests or integration-level CSRF coverage.

The mobile authentication service checks now require a usable persisted access token, its user/device/scopes, the access deadline and both refresh deadlines after a valid exchange. Invalid client/callback, short/long/nonconforming verifier, unknown or wrong-client refresh, exact refresh idle expiry and revoked-device ticket issuance must leave credentials or code consumption unchanged as appropriate. Malformed verifier examples use a matching challenge so a later proof mismatch cannot hide removal of the format check. Existing code replay, refresh reuse with family revocation, inactive-user token denial and single-use web-ticket cases remain separate. These checks are included in the green 3,310-test suite; their refreshed mutation matrix is still required.

Session controller and inactive-session integration tests now share one source experiment after confirming that both previous profiles generated the same 138 method candidates; the session/proof models contribute declarations without method candidates. The integration boundary remains a separate review alias and retains real CSRF protection, inactive member/guest password and code denial, first-request session/subscription cleanup and denied account changes. New controller checks require sign-in links to be consumed before account-completion staging and rechecked from the locked row after a stale initial lookup. Existing cases now require independent bounce/complaint reset, invalid pending-link cleanup, logout secret-token rotation, repeat logout without a session, and no failed-attempt increase for a blank password on a real password account. The initial combined suite passed 55 tests and 262 assertions and its complete comparison killed 123 of 138 mutations versus 107 in the earlier controller-only profile, with no uncovered/error/timeout rows. Later checks require HttpOnly/SameSite settings, sign-in count and logout cookie clearing, and directly exercise the shared helper against inactive input, an inactive account resolved from a provisional identity and a nameless account. Those changes passed the affected suite of 285 tests and the full suite of 3,306 tests; their refreshed controller/helper comparisons remain separately tracked.

Outcome service tests separately deny the domain operation and deny guest invitations when the actor may perform the operation itself. They require no persisted changes or notifications on rejection and require the actor to replace any supplied author on creation. A reopened-poll example also gives the actor valid recipient invitation permission while denying the outcome announcement, isolating the operation guard from the recipient guard. Direct ability checks cover closure and unrelated actors on group/direct topics. Discussion management tests distinguish authors, group coordinators, topic coordinators and members on both named topic types. Browser notification jobs now suppress delivery at exact expiry, after expiry and after revocation, then permit a still-active subscription without treating the earlier skipped attempts as delivered.

Discussion creation must also replace a supplied author with the actor and yield the persisted timeline item. The creator's reader must be saved with coordinator rights and the correct inviter. Editing topic settings must persist them and enqueue the eventless realtime update; an eventless edit must not yield a history item. A controlled interleaving revokes member editing after initial authorization but before acquiring the real topic write lock, requiring the transaction's second authorization check to reject the update. A topic coordinator who may edit still cannot invite a new guest without invitation permission. An unrelated named actor cannot discard a discussion or its topic or enqueue deletion work. Existing controller cases retain independent template-tag and guest-creator invitation/rollback checks; their service mutation coverage is reused rather than duplicating those workflows.

The channel connection regressions authenticate sockets when they open and reject missing, destroyed or inactive-owner sessions. They do not yet establish disconnection or delivery denial for an already-open socket after its session is destroyed. That boundary needs runtime validation; passing HTTP session-revocation tests does not establish the fate of an existing websocket.

Anonymous-ballot submission now has an explicit regression for a request that passes initial authorization and then waits while the voter submits before its poll lock is acquired. The transaction must recheck submission before storing another ballot. The existing detached-ballot assertions about identity links, timing metadata, immutable choices, electorate membership, reminders and exports remain intact. Method mutation does not independently establish database constraints, SQL predicates or concurrency behavior.

The Markdown profile now includes the `LoomioMarkdown` renderer and URL scrubber defined in the Redcarpet initializer. Its existing URL cases cover encoded/obfuscated unsafe schemes and preserve supported URLs; the corpus also rejects literal script and event-handler markup in Markdown input. Existing export and chatbot callers retain inline-label escaping and output-conversion behavior. Rich-text HTML input has a separate storage/sanitization contract; these Markdown-mode checks do not certify arbitrary HTML passed directly to every rendering entry point.

Four existing application problems were confirmed while production code was held fixed. Their reproductions and reviewed access boundaries are recorded in [the findings ledger](mutation_audit_findings.json):

- Viewing a discussion does not redeem its pending group membership. The helper assigns only `@group`; its discussion/poll alternatives are evaluated without assigning the local variable.
- Queued JSON and CSV group exports generate and email private data after an ordinary requester's group access is revoked. HTML exports already reauthorize at execution. A future fix must distinguish ordinary coordinator exports from the explicitly authorized operator workflow for discarded groups and selected recipient addresses.

- Bootstrap responses omit the intended `no-store` cache directive. A full Rack request confirms only `Cache-Control: no-cache`; this establishes the header mismatch, not that a browser or proxy disclosed user data.

- Customizing a built-in poll template saves its copy but fails to persist hiding the original. An authenticated controller reproduction confirms that the original remains visible after reload; this is a workflow persistence defect, not an established access disclosure.

These findings remain unresolved application work. The regular Rails suite is green because temporary failing reproductions are stored outside `test/`; their failures are retained as evidence rather than weakening their expectations or changing application behavior during the mutation comparisons.

The outbound-request review identified that WebMock responses did not establish validated-IP pinning. A focused service case now inspects the actual connection configuration and request while intercepting the transport: one DNS resolution, the validated address, TLS, timeouts, headers and body. Mixed public/private DNS is rejected at the outbound boundary; successful redirects and hop counts, and exact byte-limit behavior are checked separately. This is configuration and application-behavior evidence, not an end-to-end network penetration test. Chatbot duplicate suppression now runs both calls with valid DNS, so an unrelated fetch failure cannot hide removal of the duplicate guard.

Realtime tests now call the actual publishing method and intercept ActionCable broadcasts. Personal-plus-group, personal-plus-topic and combined destinations must produce distinct personal/shared serialization; shared scopes omit the current-user object and ID. The existing group/guest fixture roles still require active guest recipients and exclude current members with guest preferences, revoked guests, inactive guests and non-guest readers. These checks do not establish delivery denial on an already-open revoked socket. Topic-only unsubscribe checks preserve group preferences and a named direct-topic guest changes only that topic; the explicit group-wide preference workflow remains separate. The operator spam-deletion check submits trial, paid, missing and malformed group IDs and requires exactly the trial creator job. These changes passed 68 focused tests and 318 assertions and the full suite of 3,309 tests; refreshed mutation comparisons remain separately tracked.

The B3 administrative API review keeps its configured operator key separate from browser and group-administrator access. A new boundary case requires absent, empty and sixteen-character configured keys to deny administrative mutation without jobs or account changes, and a seventeen-character configured key to permit the authenticated read. Existing lifecycle denial cases now exercise both record-ID and identity routes, and identity output requires the defined public field set. The focused batch passed 24 tests and 89 assertions; the frozen full suite passed 3,310 tests and 33,339 assertions with zero failures or errors and the same two existing skips. All four checkouts matched the 2,277-file source/test manifest. The refreshed method matrix killed all 65 candidates, with complete rows and no uncovered, error or timeout verdicts. This is evidence for the selected fault model, not a complete security certification; no production authentication code changed.
