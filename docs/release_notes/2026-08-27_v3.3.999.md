# Loomio 3.3.999

Loomio 3.3.999 is an online preparation release for the irreversible
notification and topic-item migration in Loomio 3.4.0. It adds the target
notification tables and resumable consolidation tooling without changing the
application's existing notification reads, writes, API, or user interface.

- **New:** Add notification occurrence, delivery, and consolidation-state tables without replacing legacy tables
- **New:** Allow notification history to be consolidated online in resumable batches before upgrading to Loomio 3.4

## Who should install this release

Most operators do not need this release. Loomio 3.4.0 performs the same
consolidation automatically during a normal `./update.sh` and is the recommended
path for instances that do not provide an uptime guarantee.

Install 3.3.999 first only when the instance has enough notification history
that the 3.4.0 maintenance window would exceed its availability requirements.
The preparation release is based on Loomio 3.3.2 and retains the same
application behaviour and permissions.

## Install the preparation release

Make and verify a current database backup. Set
`LOOMIO_CONTAINER_TAG=3.3.999` in `.env`, then run:

```sh
./update.sh
```

The normal database migration creates additive `notification_occurrences`,
`notification_deliveries`, and `notification_consolidation_states` tables. The
legacy `events` and `notifications` tables remain authoritative, and Loomio can
return to normal service after the update completes.

Allow enough free database storage for a second representation of notification
history. Do not drop or modify the preparation tables after they have been
created.

## Warm notification history online

First run the read-only audit:

```sh
bin/rails loomio:consolidate_notifications
```

Then populate the target tables:

```sh
APPLY=1 BATCH_SIZE=250000 bin/rails loomio:consolidate_notifications
```

The apply command commits each batch and records a durable notification-ID
cursor. It can run while Loomio is serving requests, and it can be interrupted
and rerun without starting over. Adjust `BATCH_SIZE` for the available database
capacity; smaller batches reduce individual transaction size but add overhead.

The command prints the current cursor, high-water mark, and number of receipts
processed. When it finishes, run the apply command again if substantial new
notification activity was created during the first pass. A final catch-up and
complete consistency audit always run during the 3.4.0 migration.

Do not set `REPAIR` during the online warm-up. The complete low-ID repair sweep
is reserved for the 3.4.0 cutover after legacy notification writers have
stopped.

On a production-sized database, the warm pass processed about 11.5 million
legacy notification receipts in 17 minutes, or approximately 675,000 receipts
per minute. Runtime and storage depend on the database hardware and the number
and shape of notifications on the instance.

## Compatibility and rollback

This release does not change API payloads, group exports, notification
delivery, group roles, or end-user permissions. Existing 3.3 integrations
continue to work.

Rolling the application back to 3.3.2 does not require a database restore
because the preparation schema is additive and unused by the legacy runtime.
Keep the preparation tables so a later warm-up or 3.4.0 upgrade can resume. If
they must be removed, use the migration rollback while still running the
3.3.999 application; do not delete them manually.
